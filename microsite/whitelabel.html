White-labeling this template

Presets narrow the roster and gates for a use case. White-labeling goes further; it strips this repo's own identity, the name "Agentic Light", the generic multi-preset framing, the unused role files and skill dirs, so what ships looks like a tool built from scratch for exactly one job.

Not the same as a preset. Picking --preset wcag-harness configures which roles/gates/skills are active. It edits three JSON files and leaves everything else on disk untouched: System_Config/specialize.sh's own setup step says so directly: config-only gate; files are never deleted. White-labeling is the pass that comes after, deleting what specialize.sh only deselected, and rewriting the identity layer (name, CLAUDE.md, docs) around the one job the fork now does.

What white-label means here, concretely

  • Rename: "Agentic Light" stops appearing anywhere: root README.md, CLAUDE.md's title and wordmark references, microsite/template.html's <title> suffix and .wordmark text (every generated microsite page inherits both from the template), package.json-equivalent metadata if the target repo has one.
  • Strip, don't deselect: delete the preset entries, role files, and skill dirs the fork will never use, instead of leaving them selected-off in JSON. A generic fork carries all 6 roles and 12 figma-* skill dirs for optionality; a white-labeled one carries only what the one job needs.
  • Rewrite CLAUDE.md/AGENTS.md for one job: the shipped CLAUDE.md documents a generic multi-preset harness (6 roles, "pick a preset"). A white-labeled fork's version should describe the one thing this instance does, not the menu it was chosen from.
  • Narrow policy prose: GOVERNANCE.md is generated by System_Config/gen_governance.py. Its fixed prose (title, human-gate, audit-trail, config-security sections) lives in one string in that script, STATIC_TEMPLATE, which hardcodes # Governance — Agentic Light. Narrowing or renaming governance means editing that template string, not GOVERNANCE.md directly, since the next healthcheck.sh run regenerates the file and overwrites hand edits.
  • Write your own role notes: in this project only coder runs. The other roles are scope declarations. presets.json's role_notes field says what each active role means for this harness, layered on top of the generic agents/*.md text. A one-purpose fork should write notes for its own job, not inherit the ones shipped for design-harness or wcag-harness.

Walkthrough: an internal accessibility-review bot

Scenario: a team wants to ship this as their own internal tool, "our WCAG bot," with no trace of the generic template underneath. Grounded in wcag-harness's real definition in System_Config/presets.json: architect+coder+creative-director+qa, a playwright gate, the vendored wcag-audit skill, and per-role role_notes tied to that skill's audit passes.

  1. Specialize first. bash System_Config/specialize.sh --preset wcag-harness. Writes System_Config/agent-roster.json (4 active roles), pipeline/gate-config.json (playwright), System_Config/skills-selected.json (["wcag-audit"]), and System_Config/.active-preset (the preset name, which gen_governance.py reads to pick up role_notes).
  2. Commit those four files in your fork. They aren't gitignored, on purpose. In the template repo they're scratch output, but in a fork they are the fork's identity: without them a fresh clone of your harness comes back unspecialized.
  3. Delete the unused roles' files. curator and eng-manager are inactive under this preset. Removing agents/curator.md and agents/eng-manager.md is safe against healthcheck.sh's roster check (Layer B), which only validates frontmatter on the agent files that exist; it does not require all 6. The generated preset page will still list them as — inactive by name (the roster table's role list comes from the fixed set in agent-roster.schema.json, not from which files are present, which is fine for an already-decided single-purpose fork, or delete the whole presets/ section from the rewritten CLAUDE.md/docs if that framing no longer applies.
  4. Delete the unused skill dirs. Keep skills/wcag-audit/. Delete the rest: rm -rf skills/figma-* skills/server-review. That matches what skills-selected.json already says, and saves carrying 13 dead dirs around. Keep skills/wcag-audit/LICENSE and NOTICE intact: the skill is vendored under MIT, and its reference file is under the W3C Document License, which requires that notice.
  5. Extend the skill, don't replace it. wcag-audit covers the 55 WCAG 2.2 A/AA criteria. If the team has house rules on top (a stricter contrast floor, required screen readers, a component library's known issues), add them as a section in that SKILL.md or as a second skill dir next to it, so the upstream text stays diffable against its source.
  6. Rewrite the role notes. Edit wcag-harness's role_notes in presets.json to name the team's actual scope, for example which product surfaces architect reviews and which contrast floor creative-director enforces. Re-run python3 System_Config/gen_governance.py and gen_preset_pages.py; both render the notes.
  7. Prune presets.json down to one entry (or remove the concept entirely). Delete the other 5 preset objects, keep only the one this fork is. Re-run python3 System_Config/gen_preset_pages.py and python3 System_Config/gen_site.py: the first removes orphaned preset pages and the second refreshes dashboard cards and the roster table from source.
  8. Rename before regenerating. Edit microsite/template.html's <title> and .wordmark text, and the title line of STATIC_TEMPLATE in System_Config/gen_governance.py. Every generated page (preset pages via gen_preset_pages.py, index.html's marker blocks via gen_site.py) inherits from the HTML template, and GOVERNANCE.md from STATIC_TEMPLATE. Rename, then re-run all three generators. Re-running before the rename just bakes the old name back in.
  9. Rewrite CLAUDE.md. Replace the generic "6 roles, pick a preset" framing with a description of the one thing this fork does: an internal accessibility-review bot for this team, not a template.
  10. Tighten what specialize.sh left generic. A single-purpose harness may still replace its preset's default gate list with an exact project-specific contract. Keep the human approval gate and other pipeline safety checks intact. GOVERNANCE.md's gate-policy section regenerates from gate-config.json, so it follows automatically.

What NOT to touch

The mechanism stays. Only the identity and scope narrow.

  • Gate/pipeline mechanics in pipeline/run.sh, pipeline/lib/: the ordered gate-run, human-approval, and PR-draft flow doesn't change per fork.
  • Session logging: System_Config/log_session.sh and its output shape stay as-is.
  • Healthcheck's layered structure: System_Config/healthcheck.sh's PASS/WARN/FAIL layers keep working against whatever roster/skill files remain; they don't assume all 6 roles or all 12 skills exist.
  • The generator logic (gen_site.py, gen_preset_pages.py, gen_governance.py): don't fork or hand-edit their functions; they already handle a pruned presets.json, a trimmed agents/ dir, and presets with or without role_notes. The one exception is gen_governance.py's STATIC_TEMPLATE string: that's prose, not logic, and it's where renaming and narrowing governance happens.
  • The pipeline's safety checks: the human approval gate, the gate-config validation, and any other pre-commit checks in pipeline/run.sh. Narrowing a fork is not a reason to loosen them.
