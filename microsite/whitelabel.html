White-labeling this template

Presets narrow the roster and gates for a use case. White-labeling goes further; it strips this repo's own identity, the name "Agentic Light", the generic multi-preset framing, the unused role files and skill dirs, so what ships looks like a tool built from scratch for exactly one job.

Not the same as a preset. Picking --preset wcag-harness configures which roles/gates/skills are active. It edits three JSON files and leaves everything else on disk untouched: System_Config/specialize.sh's own setup step says so directly: config-only gate; files are never deleted. White-labeling is the pass that comes after, deleting what specialize.sh only deselected, and rewriting the identity layer (name, CLAUDE.md, docs) around the one job the fork now does.

What white-label means here, concretely

  • Rename: "Agentic Light" stops appearing anywhere: root README.md, CLAUDE.md's title and wordmark references, microsite/template.html's <title> suffix and .wordmark text (every generated microsite page inherits both from the template), package.json-equivalent metadata if the target repo has one.
  • Strip, don't deselect: delete the preset entries, role files, and skill dirs the fork will never use, instead of leaving them selected-off in JSON. A generic fork carries all 6 roles and 12 figma-* skill dirs for optionality; a white-labeled one carries only what the one job needs.
  • Rewrite CLAUDE.md/AGENTS.md for one job: the shipped CLAUDE.md documents a generic multi-preset harness (6 roles, "pick a preset"). A white-labeled fork's version should describe the one thing this instance does, not the menu it was chosen from.
  • Narrow policy prose: if your fork carries a GOVERNANCE.md (this template does not ship one yet), the same narrowing applies: rewrite its generic role-framing around the one specialization, rather than leaving 6-role language that no longer describes what's active.

Walkthrough: an internal accessibility-review bot

Scenario: a team wants to ship this as their own internal tool, "our WCAG bot," with no trace of the generic template underneath. Grounded in wcag-harness's real definition in System_Config/presets.json: architect+coder+creative-director+qa, a playwright gate, and honestly, "no shipped skill dirs cover accessibility review yet".

  1. Specialize first. bash System_Config/specialize.sh --preset wcag-harness. Writes System_Config/agent-roster.json (4 active roles), pipeline/gate-config.json (playwright), System_Config/skills-selected.json (empty, see below).
  2. Delete the unused roles' files. curator and eng-manager are inactive under this preset. Removing agents/curator.md and agents/eng-manager.md is safe against healthcheck.sh's roster check (Layer B), which only validates frontmatter on the agent files that exist; it does not require all 6. The generated preset page will still list them as — inactive by name (the roster table's role list comes from the fixed set in agent-roster.schema.json, not from which files are present, which is fine for an already-decided single-purpose fork, or delete the whole presets/ section from the rewritten CLAUDE.md/docs if that framing no longer applies.
  3. Delete the unused skill dirs. All 12 shipped dirs under skills/ are figma-*; none apply to accessibility review. Delete the lot: rm -rf skills/figma-*. This matches what skills-selected.json already says (empty for this preset); deleting just makes the filesystem agree with the config instead of leaving 12 dead dirs around.
  4. Author the missing skill. The preset's own gap note says accessibility review has no shipped skill yet. A real white-label pass writes one, skills/wcag-review/SKILL.md, rather than shipping the bot without the domain knowledge its name promises.
  5. Prune presets.json down to one entry (or remove the concept entirely). Delete the other 5 preset objects, keep only the one this fork is. Re-run python3 System_Config/gen_preset_pages.py: its orphan sweep deletes the now-unlisted pages under microsite/presets/ automatically (verified in the script: any .html under presets/ not matching a current key is removed on a real run). microsite/dashboard.html is hand-maintained, not generated; its README says to update it by hand when presets.json's shape changes, so edit its preset cards and roster table to match.
  6. Rename before regenerating. Edit microsite/template.html's <title> and .wordmark text first; every generated page (preset pages via gen_preset_pages.py, index.html's marker blocks via gen_site.py) inherits both from the template. Rename, then re-run both generators, not the other way; re-running before the rename just bakes the old name back in.
  7. Rewrite CLAUDE.md. Replace the generic "6 roles, pick a preset" framing with a description of the one thing this fork does: an internal accessibility-review bot for this team, not a template.
  8. Tighten what specialize.sh left generic. A single-purpose harness no longer needs the custom gate placeholder's escape hatch (see data-pipeline's definition, a {"name": "custom", "script": ""} stub with no script wired in) or a configurable multi-preset gate list. Recommend, once GOVERNANCE.md exists in your fork, hand-fixing the pipeline to exactly playwright plus whatever accessibility-specific check the team standardizes on, instead of leaving the gate list open-ended. This is a recommendation grounded in what specialize.sh and presets.json actually leave configurable, not a claim about specifics of hardening work not yet reviewed here.

What NOT to touch

The mechanism stays. Only the identity and scope narrow.

  • Gate/pipeline mechanics in pipeline/run.sh, pipeline/lib/: the ordered gate-run, human-approval, and PR-draft flow doesn't change per fork.
  • Session logging: System_Config/log_session.sh and its output shape stay as-is.
  • Healthcheck's layered structure: System_Config/healthcheck.sh's PASS/WARN/FAIL layers keep working against whatever roster/skill files remain; they don't assume all 6 roles or all 12 skills exist.
  • The generator scripts themselves (gen_site.py, gen_preset_pages.py): don't fork or hand-edit their logic; they already handle a pruned presets.json and a trimmed agents/ dir correctly.
